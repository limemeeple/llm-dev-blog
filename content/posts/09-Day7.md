## 임베딩의 벡터 기준은 어떻게 만드는걸까?
임베딩을 하면서 궁금한 점이 생겼다. 과연 벡터(좌표)의 기준은 무엇일까? 였다.

A라는 회사의 AI 에이전트를 만들기 위해 100 페이지의 문서 3권이 있을때
문서를 다 넣지도 않은 상태에서 벡터를 찍을 수 있는가?
아니면 제일 먼저 읽은 문서의 문장 또는 단어를 기준 벡터로 찍고 나서 거기에 맞게 퍼트리는건가?

이런 의문이 생겨서 알아보기로 했다.

## 벡터의 기준은 문서가 아니라 임베딩 모델이다.
애초에 내 생각은 틀렸다. 문서를 돌리면 처음으로 벡터를 찍는것이 아니었다.
**이미 학습이 끝난 모델에 텍스트를 넣으면 벡터가 나오는 것'이었다.
```
vector = f(text)
```
여기서 'f'는 OpenAI의 text-embedding-3, BGE, E5 같은 사전학습된 모델이고, 가중치는 이미 고정되어 있다. 좌표계는 문서를 넣기 훨씬 전에 이미 만들어져 있는 셈이다.

[정리하자면]
- 3권을 다 읽고 벡터를 찍을 필요도 없고 첫 문서를 기준점으로 잡지도 않는다.
- 각 청크는 서로 완전히 독립적으로 변환된다.
- 3권을 거구로 넣어도 벡터 결과는 똑같다. 순서 의존성이 0이다.

## 만약 이미 벡터로 지정되지 않는 새로운 단어가 있다면? '없는 단어'는 존재할 수 없다.
현재 임베딩 모델에는 단어 사전이 없고 **서브워드(subword)사전**이 있을 뿐이라고 한다.
```
"카카오뱅크아파트론"  →  ["카카오", "뱅크", "아파", "트", "론"]
"Quantalyzer"        →  ["Quant", "aly", "zer"]
"XKQ-7741"           →  ["XK", "Q", "-", "77", "41"]
```
BPE나 SentencePiece는 모르는 문자열을 만나면 조각으로 쪼갠다. 최후의 보루로 바이트 단위까지 내려가기 때문에, 이론상 쪼개지지 않는 입력은 없다고 한다. 이모지, 한자, 처음보는 사내 코드명 전부 마찬가지로...

그래서 벡터는 반드시 나온다고 한다. 문제는 벡터가 나오냐가 아닌 **의미가 맞느냐**다.

#### 벡터의 품질은 세 가지에 달려 있다.
1. 조각들이 의미를 얼마나 보존하는가
'카카오 + 뱅크'는 운이 좋은거다. 조각 자체가 유의미하니깐 합선된 벡터도 '금융 서비스'근처에 착지한다.
반면에 'XK+Q+77+41'같이 의미가 없는 조각들은 벡터는 나오지만 임베딩 공간의 별 의미 없는 지점에 떨어진다.

2. 주변 문맥(중요)
Transformer는 청크 전체를 attention으로 함께 처리한다. 예를 들어 
'XKQ-7741은 사내 전자결재 시스템으로, 휴가 신청과 품의서 상신에 사용된다.'
'XKQ-7741'이라는 토큰 조각들이 '전자결재', '휴가 신청', '품의서'에서 의미를 빨아들인다. 결과 벡터는 **결재 시스템 영역에 안착하게 된다.** 사용자가 '휴가 신청 어떻게 해?'라고 물으면 검색이 되지만 'XKQ-7741' 라고 넣으면 기댈 문맥이 없어 사실상 무작위 위치다.

3. 형태소가 흉하게 잘렸는가
한국어에서 특히 문제다. 다국어 토크나이저가 '연차촉진제도'를 '연', '차', '촉', '진'.... 처럼 글자 단위로 부숴버리면 의미가 새어나간다.

## 임베딩을 하는 건 환각이나 잘못된 데이터 주는걸 줄여주려고 지도 자체를 작게 만든다고 보면 되는건가? 절반은 맞고, 중요한 부분은 틀렸다.
지도는 작아지지 않는다. 모델의 파라미터는 조금도 변하지 않기 때문이다. 임베딩을 아무리 해도 LLM이 아는 세계는 그대로다.
예를들면 아래와 같다.
```
임베딩 없이: "우리 회사 연차 규정 알려줘"
           → 모델이 기억에서 그럴듯하게 지어냄

임베딩 후:   "우리 회사 연차 규정 알려줘"
           → [검색] 사규 3장 2절 원문을 찾아옴
           → "다음 문서를 근거로 답하라: <원문>" 로 모델에 전달
           → 모델이 눈앞의 텍스트를 읽고 답함
```
환각이 줄어드는 이유는 지도를 좁혀서가 아니라 **근거를 손에 쥐여줘서(grounding)**이다.

#### 임베딩의 실제 역할은 '검색'이다.
임베딩 자체는 환각 방지 장치가 아니다. 의미 기반 검색 인덱스일 뿐이다.
RAG는 두 단계인데, 사람들이 이걸 자주 합친다.
|단계|하는 일|환각과의 관계|
|----|----|----|
|Retrieval (임베딩)|200페이지 3권에서 관련 청크를 찾아옴|직접 관련 없음. 그냥 검색.|
|Generation|찾아온 원문을 근거로 답변 생성|여기서 환각이 줄어듦|

임베딩은 '3권 중 이 세문단이 질문과 관련 있다'고 말해줄 뿐 그 문단을 읽고 답을 만드는건 여전히 LLM이고, 여전히 잘못된 답변을 할 수 있다.

#### 모델을 실제로 '제약'하는 건 프롬프트.
지도를 좁히는 역할은 임베디이 아닌 아래와 같은 문장이다.
```
주어진 문서에만 근거해서 답하라. 문서에 없는 내용은 '해당 정보를 찾을 수 없습니다'라고 답하라.
```
이걸 빼면 RAG를 구축해도 모델은 검색된 문서를 참고 삼아 자기 기억을 섞어 답한다.

#### 주의할 점
RAG는 환각을 줄이지, 없애지 않는다. 오히려 새로운 실패 모드가 생긴다.
- 검색이 틀리면 더 나빠진다. 어뚱한 청크를 가져오면, 모델은 어뚱한 문서를 근거로 자신있게 틀린 답을 말하게 된다.
- 문서에 없는 물으면 모델이 침묵하지 않고 기억에서 채워 넣는다.
- 여러 청크가 모순되면 모델이 임의로 하나를 고르거나 뒤섞는다.
- 검색은 성공했으나 모델이 원문을 미묘하게 왜고하기도 한다.

그래서 실무에서 검색 품질 평가, 근거 문장 인용 강제, "모르면 모른다고 답하기" 튜닝을 따로 챙긴다.
