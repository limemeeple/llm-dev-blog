## 규칙에 답해주는 룰 어시던트를 RAG로 만들다.

규칙 문서 스크래핑 -> 청킹 -> 로컬 다국어 임베딩 -> 벡터 DB -> 검색 -> 생성 -> 출처 표시, 그리고 평가로 검색품질을 측정하고 개선하는 사이클까지 진행하였다.

이제 그 과정을 작성해보려고 한다.

## RAG가 뭘까?
'LLM에게 묻기 전에, 관련 문서를 먼저 찾아서 프로프트에 넣어주는 것'
규칙을 찾아보게 함으로써 환각이 줄어든다.!

[RAG 파이프라인]
![alt text](../img/rag_pipeline.png)

1. 인덱싱(한번만) : 규칙문서 -> 청크로 분할 -> 임베딩(벡터)으로 변환 -> 벡터 DB에 저장.
2. 질의(매번 질문) : 질문을 임베딩 -> 벡터 DB에서 가까운 청크 검색 -> 검색한걸 근거로 LLM 답 생성.

[집고 넘어가야할 개념]
- 청킹(chunking) : 문서를 검색하기 좋은 크기의 조각으로 자르는 것.
- 임베딩(embedding) : 텍스트를 의미를 담은 숫자 벡터로 변환.
- 벡터 유사도 검색 : 직문 벡터와 가장 가까운 청크 벡트럴 찾는 것.

## 로컬라이징 - 영어데이터, 한국어 답변(트레이드오프)
아컴호러 규칙은 영어가 기준이고 한국어 규칙 소스를 찾기 어려웠다.
'한국어 원문을 구하자'라는 접근 보다는 아래와 같은 세 방법을 비교했다.

#### 방법 A : 영어로 검색하고, 답변만 한국어.
지식 베이스(규칙, 임베딩, 검색)는 영어로 두고 답변은 한구어로 하는 방식
작업량이 적고 원문을 안 건드려도 되기 때문에 규칙서의 정확도도 유지할 수 있다.
하지만 영어 질문 -> 영어 답변 보다는 매칭이 약간 떨어질 수 있다는 단점이 있다.

#### 방법 B : 규칙을 한국어로 번역해서 인덱싱.
번역 과정에서 규칙의 뉘앙스나 내용이 왜곡될 위험이 있고 해당 보드게임은 단어 하나에 판정이 바뀌는데 이걸 왜곡하게 되면 답변 자체가 틀린 답이 된다.

#### 방법 C : 영어 원문 + 한국어 번역 둘다 저장.
가장 정확할 수 있으나 저장/번역 비용이 2배가 되고 작업량도 많다.
현재 구현 과정에는 맞지 않다고 판단했다.

위 방법 중에 '방법 A'를 택하기로 했다.
근거는 **파이프 라인을 빨리 완성할 수 있고 원문 정확도도 지킬 수 있으며 확장성도 있다**고 생각했기 때문이다.

방법 A를 가능하게 하는 게 '다국어 임베딩 모델' 이다.

## 규칙 문서 긁어 오기.
ArkhamDB 규칙 페이지는 단일 HTML 페이지이기 때문에 스크래핑이 쉽고 용어집 구조라 청킹에도 유리하다.

- 스크래핑 : 웹사이트에서 AI 학습이나 분석에 필요한 데이터를 추출·수집하는 기술 

스크래핑을 하기위해 'BeautifulSoup' 라이브러리를 사용하기로 했다.

- BeautifulSoup : 파이썬(Python)에서 HTML 및 XML 문서를 파싱하고 데이터를 추출하는 데 사용되는 대표적인 웹 스크래핑(크롤링) 라이브러리

```
import requests
from bs4 import BeautifulSoup

URL = "https://arkhamdb.com/rules"

def scrape_rules() -> str:
    resp = requests.get(
        URL, timeout=10,
        headers={"User-Agent": "ArkhamPortfolioBot/0.1 (learning project)"},
    )
    resp.raise_for_status()
    soup = BeautifulSoup(resp.text, "html.parser")

    content = soup.find(id="rules")   # id로 집는 게 class보다 확실
    if content is None:
        content = soup.body            # 폴백
    return content.get_text(separator="\n", strip=True)
```

## 청킹 - 크기와 겹침(overlap)의 트레이드 오프
청킹은 '얼마나 크게, 어떨게 자르냐'에 따라 검색 품질이 크게 차이 난다.

[문맥 분할(Chunking) 알고리즘이나 프롬프트 지침]
- 크기(Size) : 한 번에 처리하거나 불할할 텍스트이 단위(주로 글자 수, 단어 수, 토큰 수)를 뜻함.
- 겹침(Overlap) : 텍스트를 분할할 때 이전 조각의 끝부분과 다음 조간의 시작 부분이 겹치는 정도.
- 경계 존중 : 글을 쪼갤 때 설정한 크기에 딱 맞춰서 단어를 억지로 자르지 않고, 온전한 문장이나 문단 단위가 끝나는 지점에서 분할한다는 원칙.

[크기에 따른 트레이드 오프]
- 너무 클 경우 : 한 청크에 여러 주제가 섞여 임베딩 벡터가 '흐려진다', 검색도의 정확도가 떨어진다, 토큰이 낭비된다.
- 너무 작을 경우 : 문맥이 잘린다. 쓸모없는 청크가 된다.

'임베딩 모델은 입력 길이 상한(max sequence length)이 있다. 
다국어 MiniLM 계열은 상한이 짧은 편(대략 128토큰)이어서 그것보다 길면 뒤가 잘려나간다고 한다.
영어 기준으로 1토큰 = 4글자로 하니 500자 정도로 시작하기로 하고 'max sequence length'에 맞춰 조정했다.

[겹침(overlap)이 필요한 이유]
문단 경계로 잘라도 연속된 두 조각 사이에 걸친 정보는 온전치 않을 수 있다.
```
ex> A라는 행동은 B 행동이 종료된 시점에서 발생한다.
해당 규칙이 마침 청크 경계에 걸려 
'A라는 행동은 B 행동이 종료된'
'시점에서 발생한다.'
두 개의 청크에 담길 경우 반쪽자리 규칙이 돼버리고
검색이 제대로 잡지 못할 수 있다.
```
그래서 직전 청크의 꼬리 일부를 다음 청크 앞에 겹쳐서 넣는다고 한다.
보통 청크 크기의 10~20%를 겹친다고 한다.

[겹침의 트레이드 오프]
- 겹침을 늘리면 : 경계 문맥이 더 잘 보존되지만 중복이 늘어 저장 용량, 검색 노이즈, 토큰이 증가한다.
- 겹침을 줄이면 : 날렵하지만 경계 정보를 잃을 위험이 커진다.

```
def chunk_text(text: str, chunk_size: int = 500, overlap: int = 80) -> list[dict]:
    paragraphs = [p.strip() for p in text.split("\n") if p.strip()]  # 경계 존중
    raw_chunks, current = [], ""

    for para in paragraphs:
        if current and len(current) + len(para) + 1 > chunk_size:
            raw_chunks.append(current)
            tail = current[-overlap:]      # 직전 청크 꼬리 = 겹침
            current = f"{tail}\n{para}"
        elif current:
            current = f"{current}\n{para}"
        else:
            current = para

    if current:
        raw_chunks.append(current)

    # id를 붙여 dict로 (벡터 DB 저장·출처 추적의 키가 됨)
    return [{"id": f"chunk_{i}", "text": c} for i, c in enumerate(raw_chunks)]
```
해당 코드를 실행 했더니 **청크 665개, 평균 425자**로 목표 근처에 왔다.
하지만 부작용이 하나 발견 됐는데 'current[-overlap:]'가 글자 단위로 자르다 보니 단어 중간에서 끊긴 걸 확인 했다.(해당 로그에서는 'boo', 'k'로 끊긴걸 확인했다.)

이를 더 다듬기 위해 아래와 같은 코드를 추가했다.
```
tail = current[-overlap:]
tail = tail[tail.find(" ") + 1:]   # 첫 공백 이후부터 → 잘린 단어 조각 버림
```

## 임베딩 + 벡터DB(Chroma)
벡터 저장은 Chroma로 정했다. 로컬 디스크에 저장되는 부분에서 선택했다.

Chroma로 임베딩을 대신하게 하는데 이유는 '넣을 때(add)도 검색(query)도 같은 모델로 벡터화 해주기 때문이다.

임베딩 모델은 자기만의 좌표계가 있어서 모델 A, 모델 B 혼용해서 사용하게 되면 같은 질문과 청크인데도 불구하고 이상한 검색이 나오거나 할 수 있다. 이런 점은 에러는 없지만 결과만 이상하게 나와 디버깅이 힘들다.

Chroma에 임베딩 함수를 컬렉션에 붙여두면 일관성을 자동으로 강제해 줄 수 있다.

- collection.add(documents=[...]) : 청크를 넣을 때 Chroma가 등록된 embed_fn으로 자동 임베딩해서 저장.
- collection.query(query_texts=[...]) : 질문으로 검색할때도 Chroma가 같은 embed_fn으로 질문을 임베딩해서 비교.

#### 만약 손으로 하면 어떻게 하면 될까?
```
# (직접 하는 방식 — '안' 쓴 방식)
model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")

# 저장할 때: 내가 직접 임베딩해서 넣고
collection.add(ids=ids, embeddings=model.encode(texts), documents=texts)

# 검색할 때도: 내가 직접, '같은 모델로' 임베딩해서 넣어야 함
collection.query(query_embeddings=model.encode([question]))
```
두 곳에서 같은 'model'을 쓰는 걸 전적으로 내가 책임져야 한다.

[Chroma에게 임베딩을 맡기는 것에 대한 트레이드 오프]
- Chroma 에게 맡기면 : 간편하고 안전하지만 임베딩이 언제 어떻게 일어나는지 Chroma 내부로 숨김.
- 직접 encode 하면 : 번거롭고 실수 위험이 있지만, 임베딩 벡터를 중간에 가공하거나(정규화, 캐싱), 배치 크기를 세밀하게 조절하는 등의 **제어권**을 가질 수 있다.

```
import chromadb
from chromadb.utils import embedding_functions

# 로컬 다국어 임베딩 (내부에서 sentence-transformers → 소버린 OK)
embed_fn = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="paraphrase-multilingual-MiniLM-L12-v2"
)
client = chromadb.PersistentClient(path="./chroma_db")   # 디스크에 저장
collection = client.get_or_create_collection(
    name="arkham_rules",
    embedding_function=embed_fn,
    metadata={"hnsw:space": "cosine"},   # 코사인 거리
)

def build_index(chunks: list[dict]) -> None:
    if collection.count() > 0:            # index-once: 재실행 시 재임베딩 방지
        print(f"이미 인덱싱됨: {collection.count()}개 — 건너뜀")
        return
    collection.add(
        ids=[c["id"] for c in chunks],
        documents=[c["text"] for c in chunks],  # Chroma가 자동 임베딩
    )

def retrieve(query: str, k: int = 3) -> list[dict]:
    results = collection.query(query_texts=[query], n_results=k)
    return [
        {"id": cid, "text": doc, "distance": dist}
        for cid, doc, dist in zip(
            results["ids"][0], results["documents"][0], results["distances"][0]
        )
    ]
```
위 코드를 보면 'index-once'패턴을 사용하였는데 한번 인덱싱해서 디스크에 저장하면 재실행이 빨라지지만 청크 크기/모델을 바꾸면 './chroma_db'를 지우고 다시 인덱싱 해야 한다.
**./chroma_db도 원문에서 파생된 데다 용량이 커서 .gitignore 대상이다**

## 생성(RAG의 G) + 출처 표시
검색된 청크를 프로프트에 근거로 넣고 LLM에게 답을 시키기로 했다.
그리고 해당 청크를 답변과 같이 반환함으로써 근거가 무엇인지 보여주기로 했다.

```
import anthropic
from dotenv import load_dotenv

load_dotenv()
client = anthropic.Anthropic()
MODEL = "claude-haiku-4-5-20251001"

SYSTEM = """너는 아컴호러: 카드게임 규칙 도우미야.
아래 <규칙> 안의 내용만 근거로 한국어로 답해.
규칙에 없는 내용은 지어내지 말고 '규칙 문서에서 찾지 못했어요'라고 말해."""

def answer(question: str, k: int = 3) -> dict:
    sources = retrieve(question, k=k)                 # 검색
    context = "\n\n---\n\n".join(s["text"] for s in sources)  # 증강

    user_message = f"<규칙>\n{context}\n</규칙>\n\n질문: {question}"

    response = client.messages.create(                # 생성
        model=MODEL, max_tokens=1024, system=SYSTEM,
        messages=[{"role": "user", "content": user_message}],
    )
    return {"answer": response.content[0].text, "sources": sources}
```
